# Reading the results

This is a field guide to the two data files this benchmark produces, for
anyone who wants to check a claim in [`README.md`](README.md) against the
underlying numbers or compute a different cut themselves. It does not
introduce any numbers not already in `README.md` or the committed
`results/` files.

## The two files

| File | What it is | Rows |
|---|---|---|
| [`results/raw_results.jsonl`](results/raw_results.jsonl) | One JSON object per agent run — the unit of measurement | 90 (45 questions x 2 conditions) |
| [`results/summary.json`](results/summary.json) | `raw_results.jsonl` aggregated by condition and by `question_type` x condition | Generated by `analyze_results.py`, never hand-edited |

Both are committed to this repo (unlike `data/pdfs/` and `data/corpus.jsonl`,
which are regenerated locally). If you re-run `analyze_results.py` against
the committed `raw_results.jsonl`, you should get byte-for-byte the same
`summary.json` back; that round trip is a cheap way to sanity-check the
aggregation code without running the agent at all:

```bash
python3 analyze_results.py --out /tmp/summary_check.json
diff /tmp/summary_check.json results/summary.json
```

## `raw_results.jsonl` schema

One line per (question, condition) pair:

| Field | Meaning |
|---|---|
| `financebench_id` | FinanceBench's own question id |
| `question_type` | `metrics-generated`, `domain-relevant`, or `novel-generated` (FinanceBench's own categories) |
| `doc_name` | The gold source filing for this question |
| `condition` | `keyword` or `vector` — which tool the agent had |
| `question` / `reference_answer` | FinanceBench's question and reference answer, verbatim |
| `final_answer` | What the agent actually answered |
| `correct` | Output of `evaluate.is_correct(final_answer, reference_answer)` — see "Answer correctness" below |
| `hit_evidence` | Did any tool call in this run return the gold `(doc_name, page_num)`, ±1 page? |
| `turns_used` | ReAct turns consumed (max 4, see `agent.MAX_TURNS`) |
| `n_tool_calls` | Number of search calls the agent made |
| `wall_clock_s` | End-to-end latency for this run |
| `tool_calls` | Every query the agent issued and the hits it got back: `[{"query": str, "hits": [[doc_name, page_num, score], ...]}]` |

## Two different metrics, two different failure modes

The README's "What this actually shows" section covers this in the context
of the actual results; this is the short, standalone version for reference.

**`hit_evidence` (evidence recall)** answers one narrow, mechanical
question: *did the retrieval tool surface the correct page?* It's a page
number comparison, not a judgment call, which makes it the more mechanically
trustworthy of the two metrics — there's no ambiguity in what it measures,
only in whether "the right page" is a well-posed question for a given query
(it can be, even when the retrieved page didn't help the model answer).

**`correct` (answer correctness)** answers a different, entangled question:
*did the agent's final answer match the reference?* This depends on
retrieval quality **and** on whether a 3B model can read the right number
back out of a page of dense financial-table text once it has it, **and** on
whether the model already "knew" the answer from pretraining and didn't need
retrieval at all. All three of those are folded into one pass/fail bit, and
`evaluate.py`'s numeric-tolerance heuristic (see below) adds a fourth source
of noise on top.

Concretely: a condition can have **high evidence recall and low answer
correctness** (the model found the right page and still got the number
wrong — see `metrics-generated__vector` in `results/summary.json`, 60%
recall vs 6.7% correct), or **low evidence recall and high answer
correctness** (the model answered right without needing the tool — see
`domain-relevant__keyword`, 0% recall vs 53.3% correct). Neither is a bug in
the measurement; they're two different things being measured, and reporting
only one of them would hide whichever failure mode it doesn't cover.

**If you only look at one number in `summary.json`, look at
`evidence_recall`, not `answer_correct`**, for a read on retrieval quality
specifically. Use `answer_correct` for a read on end-to-end task success,
with the understanding that it's gated by the local model's extraction
ability as much as by retrieval.

## The answer-correctness heuristic, precisely

`evaluate.is_correct()` (also documented in `README.md`'s Limitations
section, repeated here because it materially affects how to read
`answer_correct`):

1. Extract every number-like token from both the predicted and reference
   answer (`$1,577.00`, `63.4%`, `2.5 billion`, etc.), normalizing
   `billion`/`million`/`thousand`/`%` suffixes to a plain float.
2. If the reference answer contains at least one number, the run counts as
   correct if **any** extracted predicted number is within 2% relative
   tolerance of **any** extracted reference number.
3. If the reference answer has no number in it (a small minority of
   FinanceBench answers), fall back to case-insensitive substring
   containment of the reference in the prediction.

This is **not** an LLM-judged score. It will mark a verbose, correct
free-text answer wrong if it never states a matching number, and it will
mark a numerically-correct-but-reasoning-wrong answer right. It was chosen
specifically to avoid introducing a second model's own judgment error into
the measurement — see `README.md` Limitations for the tradeoff.

## Recomputing a different cut

`analyze_results.py` only reports overall-by-condition and
by-`question_type`-by-condition. Any other cut (by `doc_name`, by
`turns_used`, correlating `n_tool_calls` with `correct`, etc.) is a normal
`jsonlines` read away:

```python
import json

with open("results/raw_results.jsonl") as f:
    rows = [json.loads(line) for line in f]

# Example: answer correctness for questions the vector tool actually found evidence for
hits = [r for r in rows if r["condition"] == "vector" and r["hit_evidence"]]
print(sum(r["correct"] for r in hits) / len(hits))
```
